# 코딩 에이전트의 고통은 불안·혼란·불투명에서 온다

기존 AI 코딩 에이전트의 고통은 대부분 모델 성능이 아니라 모델을 감싼 앱에서 나온다. 사용자들이 반복해서 호소하는 문제는 무겁고 느린 Electron GUI, 깜빡이고 스크롤이 튀는 TUI, 거의 기계적으로 누르게 되는 승인 창(Claude Code 사용자는 권한 요청의 **93%를 승인**한다), 파일명까지 숨겨 버리는 툴 호출 접기, 예고 없이 일어나는 컨텍스트 압축(compaction), 무엇이 할당량을 잡아먹는지 알 수 없는 사용량 계측, 믿기 어려운 되돌리기, 그리고 증거 없이 나오는 "테스트 통과" 주장이다. 사용자의 세 가지 설계 목표에 맞춰 다시 묶으면 편안함을 해치는 것은 **불안**(내 작업을 잃거나 망가뜨릴지 모른다는 두려움), 초보자를 막는 것은 **보이지 않음과 되돌릴 수 없음**, 투명성을 무너뜨리는 것은 **요약만 있고 증거가 없는 UI**다. 인기 제품 중 OpenAI Codex 앱과 Claude 데스크톱 앱(Code 탭)은 "에이전트 관제실"이라는 같은 형태로 수렴했다. 공통 요소는 세션별 git worktree 자동 격리, diff 위 인라인 코멘트, 앱 안에서 끝나는 커밋과 PR, 스케줄 자동화, 기존 구독에 번들된 가격이다. 두 앱이 인기를 얻은 이유는 모델이 장시간 자율 작업을 할 수 있게 된 시점에 여러 에이전트를 한꺼번에 감독할 화면을 제공했기 때문이다. **lazycodex.ai는 데스크톱 앱이 아니다.** Codex 위에 얹는 오픈소스 하네스 플러그인이고, 핵심 주장은 "에이전트의 '끝났다'를 믿지 말고 증거로 검증하라"다. 따라서 새 앱이 차별화할 여지는 기능을 더 넣는 데 있지 않다. 차별화 지점은 조용하고 정돈된 화면, 되돌릴 수 있는 범위를 미리 보여 주는 안전망, 턴마다 쌓이는 비용 기록, 증거에 묶인 완료 표시, 그리고 경쟁 제품들이 1년 넘게 고치지 못한 한국어 IME 입력이다.

## lazycodex는 앱이 아니고, Codex와 Claude 앱은 '관제실'로 수렴했다

### lazycodex.ai: GUI 없는 검증 규율 레이어

lazycodex.ai는 스스로를 "Codex agent harness"이자 "A light port of OmO's Hephaestus, for Codex"라고 소개한다. MIT 라이선스 오픈소스이고, code-yeongyu가 만든 oh-my-openagent(OmO)를 Codex용으로 가볍게 포장한 배포판이다 ([lazycodex.ai](https://lazycodex.ai/)). GitHub 설명도 이를 **"Project memory, planning, execution, and verified completion inside Codex"**라고 요약하며, 독립 앱이 아니라 `npx lazycodex-ai install`로 설치하는 Codex 플러그인으로 배포된다 ([GitHub](https://github.com/code-yeongyu/lazycodex)). 사용법은 창을 다루는 방식이 아니라 명령 중심 워크플로다. `$init-deep`은 계층형 AGENTS.md 프로젝트 메모리를 만든다. `$ulw-plan`은 구현 전에 "decision-complete" 계획을 `plans/<slug>.md`에 쓰고 제품 코드는 건드리지 않는다. `$start-work`는 그 계획의 체크리스트를 디스크에 저장되는 진행 상태와 엄격한 TDD로 실행한다. `$ulw-loop`는 검증된 완료에 이를 때까지 반복하며, ultrawork 모드 상한은 500회, 일반 모드는 100회다 ([lazycodex.ai](https://lazycodex.ai/); [Easton Dev, 2026-07-28](https://eastondev.com/blog/en/posts/ai/20260728-lazycodex-codex-agent-harness/)). 제3자 리뷰가 꼽는 장점은 계획과 실행의 분리, 세션을 넘어 이어지는 계층형 컨텍스트, 5개의 evidence gate(계획 재확인, 자동 검증, 수동 QA, 적대적 점검, 정리)다. 단점으로는 설정 부담, 한 파일짜리 수정에는 과하다는 점, "완료"를 주장해도 여전히 사람이 확인해야 한다는 점을 든다 ([Easton Dev](https://eastondev.com/blog/en/posts/ai/20260728-lazycodex-codex-agent-harness/)). 인기 규모는 불확실하다. 사이트는 GitHub 스타를 1.9k로 표기하지만 조사 시점 GitHub 페이지에서는 3.7k였다. 인기 원인을 직접 분석한 자료는 찾지 못했다. 설치가 한 줄이고 Codex 구독 쿼터를 그대로 쓰는 무료 도구라는 점이 원인일 것이라는 추정만 가능하다. 새 앱 설계에 주는 교훈은 UI가 아니라 개념이다. 계획을 파일로 남기는 1급 산출물로 다루고, "완료"를 증거로 통제하는 것이 핵심이다. 이는 뒤에서 다룰 "거짓 완료" 고통에 커뮤니티가 스스로 만든 답이다.

### OpenAI Codex 앱: 여백 있는 병렬 관제실

Codex 앱은 **2026-02-02 macOS**, 2026-03 Windows로 출시됐고, **2026-07-09 ChatGPT 데스크톱 "슈퍼앱"에 흡수**되어 Chat / Work / Codex 세 모드 중 하나가 됐다. 2026-03 기준 주간 활성 개발자는 200만 명 이상이었다 ([Wikipedia](https://en.wikipedia.org/wiki/Codex_(AI_agent)); [IntuitionLabs](https://intuitionlabs.ai/articles/openai-codex-app-ai-coding-agents)). 구조는 프로젝트별 스레드, 기본으로 켜져 있는 git worktree, 스레드 옆 diff 패인으로 이뤄진다. diff 패인에서는 인라인 코멘트, 청크나 파일 단위 stage·revert, commit, push, PR 생성까지 할 수 있다. 코드 편집 자체는 "Open with" 메뉴로 Cursor, Zed, 터미널 같은 외부 도구에 넘긴다 ([Codex worktrees 문서](https://developers.openai.com/codex/app/worktrees); [Catalin's Tech, 2026-06-12](https://catalins.tech/codex-vs-claude-code-desktop-apps/)). Automations는 지시문, 스킬, 트리거를 묶어 스케줄로 실행하고 결과를 **리뷰 큐**에 쌓아 사람의 승인을 기다리게 한다 ([IntuitionLabs](https://intuitionlabs.ai/articles/openai-codex-app-ai-coding-agents)). 칭찬은 병렬성과 정돈된 인상에 집중된다. 출시 당시 반응은 "5–10개 에이전트 병렬", 개발자가 작성자(author)에서 지휘자(conductor)로 바뀐다는 것, "Automations가 가장 과소평가된 기능"이라는 것이었다 ([Latent Space](https://www.latent.space/p/ainews-openai-codex-app-death-of)). 디자인 비교 글은 여백이 넉넉해 덜 답답하고 **"사람이 디자인한 것 같아 더 프로페셔널"**하다고 평했다 ([Catalin's Tech](https://catalins.tech/codex-vs-claude-code-desktop-apps/)). 약점도 있다. 프론트엔드 결과물이 "bland"해서 Claude로 돌아갔다는 평이 있는데, 이는 앱보다 모델 성향의 문제다 ([XDA, 2026-07-16](https://www.xda-developers.com/codex-technically-better-than-claude-code-stopped-using-it-for-one-specific-reason/)).

### Claude 데스크톱 앱(Code 탭): 기능 밀도가 가장 높은 에이전트 IDE

Claude 데스크톱은 Chat / Cowork / Code 3탭 구조다. Code 탭은 **2026-04-14 재설계**로 멀티세션 사이드바(세션마다 worktree 자동 격리)와 드래그 앤 드롭 패인을 갖췄다. 패인 종류는 Chat, Diff, Browser, Terminal, File, Plan, Tasks, iOS Simulator 등이다 ([Build Fast with AI](https://blog.buildfastwithai.com/claude-code-desktop-redesign-2026)). 공식 문서 기준으로 기능을 보면, 권한 모드는 Manual, Accept edits, Plan, Auto, Bypass 다섯 단계다. diff 줄 코멘트를 모아 한 번에 제출할 수 있고 "Review code" 버튼이 있다. PR을 만든 뒤에는 CI 상태 바와 Auto-fix, Auto-merge 토글이 붙는다. 모델 선택기 옆 **usage ring**은 세션 컨텍스트와 플랜 사용량을 함께 보여 준다. 트랜스크립트 밀도는 Normal, Thinking, Verbose 세 단계로 고른다. 메인 대화를 오염시키지 않는 side chat(`/btw`)도 있다 ([Claude Code Docs: Desktop](https://code.claude.com/docs/en/desktop)). 클라우드 세션은 2026-09-23 GA가 됐다. 노트북을 닫아도 계속 돌고, `--teleport`로 로컬에 넘겨받을 수 있다 ([AICoder](https://aicoder.com/news/news-20260923-claude-code-cloud-sessions-ga)). CLI와 설정을 공유하고 `/desktop`, `/resume`으로 세션을 옮길 수 있다는 점이 생태계 차원의 강점이다. 반면 비판은 정확히 사용자가 노리는 지점에 몰려 있다. 앱이 **"busy and crowded"**하고 기능이 탭마다 흩어져 있으며, 스킬 설치에 5번 클릭해야 하고(Codex는 2번), 외관이 "AI가 만든 것 같다"는 것이다 ([Catalin's Tech](https://catalins.tech/codex-vs-claude-code-desktop-apps/)).

### 왜 인기인가, 그리고 무엇이 수렴했나

두 앱의 인기는 세 가지가 겹친 결과로 보인다. 첫째, 모델 도약이다. Codex 사용량은 GPT-5.2 이후 두 배 넘게 늘었고 GPT-5.2-Codex 사용량은 2025-08 대비 20배가 됐다 ([IntuitionLabs](https://intuitionlabs.ai/articles/openai-codex-app-ai-coding-agents)). 둘째, 여러 작업을 동시에 감독할 화면이 필요해졌다. 셋째, 추가 비용이 없었다. Codex는 2026-07 이후 Free 플랜까지 포함되고, Claude 클라우드 세션은 별도 컴퓨트 요금 없이 구독 레이트리밋을 공유한다 ([TechTimes](https://www.techtimes.com/articles/320087/20260710/chatgpt-work-free-every-plan-what-openais-codex-merger-changes-you.htm); [AICoder](https://aicoder.com/news/news-20260923-claude-code-cloud-sessions-ga)). 관제실 패턴 자체는 Conductor, CodexMonitor 같은 서드파티가 먼저 선보였다는 지적도 있다 ([Latent Space](https://www.latent.space/p/ainews-openai-codex-app-death-of)). 수렴한 패턴 가운데 차용할 가치가 있는 것은 다음과 같다.

| 수렴 패턴 | Codex 앱 | Claude 앱 | 새 앱에 대한 의미 |
|---|---|---|---|
| 세션별 격리 | worktree 기본 활성 ([Releasebot](https://releasebot.io/updates/openai/codex)) | 세션마다 자동 worktree, `.worktreeinclude`로 `.env` 복사 ([Docs](https://code.claude.com/docs/en/desktop)) | 병렬 충돌을 UX 차원에서 제거. 단, "지금 어디서 일하나" 혼란이 새로 생긴다(아래 참조) |
| diff 위 피드백 | 인라인 코멘트, 청크 stage/revert | 줄 코멘트 일괄 제출(Cmd+Enter), AI "Review code" | diff를 대화 인터페이스로 만든다 |
| 앱 내 git/PR | commit·push·PR | PR CI 상태바, Auto-fix/Auto-merge, 머지 시 세션 자동 아카이브 | 초보자에게는 git 용어를 숨긴 채 같은 기능을 제공할 여지가 있다 |
| 백그라운드 결과 처리 | Automations → 리뷰 큐 | Routines(스케줄/API/GitHub 이벤트) | 결과를 인박스처럼 "검토 대기"로 모은다 |
| 사용량 가시성 | 모델 tier·effort 선택 ([Developers Digest](https://www.developersdigest.tech/blog/chatgpt-work-codex-desktop-app)) | usage ring(컨텍스트 + 플랜) | 항상 보이는 계기가 기본 사양이 됐다 |
| 권한 표현 | 샌드박스 × 승인 정책 2축, 리뷰어 에이전트 자동 판정 ([Codex docs](https://developers.openai.com/codex/agent-approvals-security)) | 모드 하나 선택 + 백그라운드 안전 분류기 | 사용자에게는 하나의 선택지, 내부적으로는 2축 |
| 외부 도구 연결 | "Open with" 외부 에디터 | 브라우저·터미널·시뮬레이터를 패인으로 내장 | 내장할지 위임할지는 화면 복잡도와의 트레이드오프다 |

## 편안함을 깨는 것은 무거운 화면, 승인 피로, 설명 없는 대기다

### 같은 제품인데 GUI만 느리다

Cursor, Claude 데스크톱, Codex 데스크톱은 모두 Electron 기반이다. 세 제품 모두에서 "CLI나 브라우저판은 멀쩡한데 데스크톱만 느리다"는 이슈가 2026년까지 반복된다. Cursor는 공식 블로그에서 크래시 대부분이 **메모리 부족(OOM)** 때문이라고 인정했다. 원인은 과도한 로딩으로 생기는 급성 OOM과 리소스 누수로 쌓이는 누적 OOM이었다 ([Cursor 블로그, 2026-04-21](https://cursor.com/blog/app-stability)). 128GB RAM에 76GB가 비어 있어도 렌더러 OOM이 약 3분마다 재현된다는 보고도 있다. 병목이 물리 메모리가 아니라 Chromium 렌더러 한도라는 뜻이다 ([Cursor 포럼](https://forum.cursor.com/t/renderer-oom-crash-code-536870904-every-3-minutes-on-windows-128gb-ram-reproducible/152534)). Claude 데스크톱에서는 Windows에서 Code 탭만 클릭할 때마다 1–5초씩 멈추고 같은 앱의 Chat 탭과 CLI는 멀쩡하다는 보고가 있다 ([claude-code#82350](https://github.com/anthropics/claude-code/issues/82350)). 렌더 루프로 18초 넘게 입력이 지연된 사례도 있다 ([#31643](https://github.com/anthropics/claude-code/issues/31643)). Codex 데스크톱에서는 스레드 하나를 시작하는 데 148초가 걸렸고 ([openai/codex#47493](https://github.com/openai/codex/issues/47493)), git 프로세스가 쌓여 물리 RAM을 98%까지 채운 일도 있었다 ([#48666](https://github.com/openai/codex/issues/48666)). 한 X 사용자는 이를 "RAM이 커도 chat과 code 탭을 오갈 때 프레임이 떨어진다. CLI가 지금까지 최고"라고 요약했다 ([X](https://x.com/CryptoEights/status/2025026273366745519)). 사용자들은 병목을 모델이 아니라 셸, 즉 대화 전체를 렌더링하는 구조와 백그라운드 프로세스 누수로 정확히 지목하고 있다. 긴 세션이나 세션이 많을 때 성능이 비례 이상으로 나빠진다는 점이 핵심이다.

CLI도 편하지 않다. Claude Code에서 가장 많은 공감을 받은 비모델 이슈는 **깜빡임과 스크롤 점프**다. "콘솔이 기록 맨 위로 스크롤된다"는 #826은 822개 반응과 354개 댓글을 받고도 여전히 열려 있다. "터미널이 제멋대로 스크롤된다"는 #3648은 836개 반응을 받았다 ([#826](https://github.com/anthropics/claude-code/issues/826); [#3648](https://github.com/anthropics/claude-code/issues/3648)). 원인은 구조적이다. Anthropic 엔지니어는 Claude Code가 alternate screen이 아니라 일반 스크롤백에 쓰기 때문에 변경이 생길 때마다 전부 지우고 다시 그려야 한다고 설명했다 ([HN](https://news.ycombinator.com/item?id=46701013)). Anthropic은 렌더러를 다시 써서 깜빡임을 **85% 줄였다**고 발표했지만 ([HN](https://news.ycombinator.com/item?id=46312507)), 같은 스레드의 사용자들은 "깜빡임 때문에 두통이 난다", "Claude가 계속 위로 스크롤돼서 오늘은 Codex를 썼다"고 적었다 ([HN: Claude Chill](https://news.ycombinator.com/item?id=46699072)). 결국 뷰포트를 직접 가상화하는 실험적 렌더러(`CLAUDE_CODE_NO_FLICKER=1`)까지 나왔는데, 발표 자체가 "트레이드오프가 있다"고 인정했다 ([Boris Cherny, X](https://x.com/bcherny/status/2039421575422980329?lang=en)). Codex, Gemini CLI, Crush도 tmux·zellij 스크롤, 깜빡임, 단축키 충돌 이슈를 각각 안고 있다 ([Codex#2558](https://github.com/openai/codex/issues/2558); [Gemini#14708](https://github.com/google-gemini/gemini-cli/issues/14708)). 터미널 출력을 깨끗하게 복사할 수 없다는 불만도 크다. 복사하면 들여쓰기와 강제 줄바꿈이 섞여 들어온다는 #18170은 296개 반응을 받았고, 붙여 넣은 텍스트가 `[Pasted ~1 lines]`로 접혀 펼칠 수 없다는 opencode #8501은 326개 반응을 받았다 ([#18170](https://github.com/anthropics/claude-code/issues/18170); [opencode#8501](https://github.com/anomalyco/opencode/issues/8501)).

### 93%가 승인되는 확인 창, 그 반대편의 rm -rf

Anthropic 엔지니어링 블로그는 **Claude Code 사용자가 권한 요청의 93%를 승인**하며, 그 결과 사람들이 무엇을 승인하는지 주의하지 않게 되는 "승인 피로"가 생긴다고 직접 밝혔다. 샌드박스는 "안전하지만 관리 부담이 크다"고도 했다 ([Anthropic Engineering](https://www.anthropic.com/engineering/claude-code-auto-mode)). 결국 사용자는 둘 중 하나를 고른다. 읽지 않고 승인하거나 `--dangerously-skip-permissions`로 전부 끈다 ([Pulumi](https://www.pulumi.com/blog/sandboxing-coding-agents-yolo-mode/)). 후자의 대가는 반복적으로 드러났다. 2025-12에는 `rm -rf tests/ patches/ plan/ ~/` 명령 하나로 한 사용자의 Mac 홈 디렉터리가 지워졌다 ([Docker 블로그](https://www.docker.com/blog/coding-agent-horror-stories-the-rm-rf-incident/)). 2026-08에는 auto 모드에서 에이전트가 직접 작성한 스크립트 안에 숨은 파괴적 코드가 `$HOME`을 지웠고, 이 이슈 스스로 **같은 유형의 다섯 번째 보고**라고 적었다 ([#88462](https://github.com/anthropics/claude-code/issues/88462)). 2026-09에도 테스트 정리 중 57,235개 파일이 삭제된 사례와 변수 치환이 드라이브 루트로 풀리면서 약 600GB가 삭제된 사례가 올라왔다 ([#93099](https://github.com/anthropics/claude-code/issues/93099); [#95426](https://github.com/anthropics/claude-code/issues/95426)). Gemini CLI에서도 `mkdir` 실패를 모른 채 존재하지 않는 경로로 `move`를 실행해 파일이 사라졌다 ([AI Incident DB #1178](https://incidentdatabase.ai/cite/1178/)). 피해자는 보통 이슈를 한 번 올리고 끝나기 때문에 반응 수는 적다. 그러나 같은 유형이 반복해서 보고되고 언론 보도가 따라온다는 점에서 파급력은 크다. 접두사 기반 허용 목록도 안전 경계가 되지 못했다. `cd x && rm …` 같은 복합 명령에서는 `cd`에 대해 권한을 묻고 ([#28240](https://github.com/anthropics/claude-code/issues/28240), 207개 반응), "권한 매칭이 근본적으로 망가졌다. 30개 이상의 이슈가 열려 있다"는 메타 이슈까지 생겼다 ([#30519](https://github.com/anthropics/claude-code/issues/30519)). 반대 방향의 고통도 있다. 에이전트가 사용자의 대답을 기다리다 **60초 뒤 답 없이 진행**해 버리는 동작에 Claude Code(#73125, 414개 반응)와 Codex(#28969, 214개 반응) 모두에서 반발이 컸다 ([CC#73125](https://github.com/anthropics/claude-code/issues/73125); [Codex#28969](https://github.com/openai/codex/issues/28969)). 사용자는 묻는 횟수를 줄이기를 원하지만, 물어볼 때는 반드시 기다리기를 원한다.

### 멈춘 건지 일하는 건지 모르는 대기

Cursor의 "Planning next moves…" 무한 대기는 74개 이상의 답글이 달린 메가스레드가 됐다. "2+2"를 물어도 멈췄다는 보고가 나올 정도였고, 결국 IDE를 재시작하는 것으로 끝났다 ([Cursor 포럼](https://forum.cursor.com/t/planning-next-moves-stuck/143985/74); [142471](https://forum.cursor.com/t/ai-stuck-on-planning-next-moves-even-on-2-2/142471)). Claude Code에서는 메인 에이전트가 한 줄을 출력한 뒤 약 18분 동안 아무것도 보여 주지 않아 서브에이전트가 멈췄는지 알 수 없었다는 보고가 있다 ([#95730](https://github.com/anthropics/claude-code/issues/95730)). 세션이 작업 중인지 사용자 입력을 기다리는지 구분되지 않는다는 보고도 있다 ([#67485](https://github.com/anthropics/claude-code/issues/67485)). Copilot agent mode는 같은 인자로 툴을 12번 연속 호출해도 반복을 감지하지 못했다. 게다가 "Continue to iterate?"가 예산을 자동으로 늘려 무인 상태로 12–18회 이상 돌았다 ([microsoft/vscode#336767](https://github.com/microsoft/vscode/issues/336767)). 이 불만들의 본질은 기다림 자체가 아니다. 네트워크 대기, 툴 실행, 모델 추론, 교착 상태를 구분할 수 없다는 **상태 설명의 부재**다. 사용자들은 실행 중에 방해하지 않고 조종하는 수단도 원한다. 작업을 끊는 대신 메시지를 큐에 넣는 기능(Claude Code #50246, 248개 반응), 흐름을 흐트러뜨리지 않는 곁가지 질문 `/btw`(opencode #16992, 399개 반응으로 opencode 2위 이슈), 완료 시 소리 알림(Codex #3962, 220개 반응)이 대표적이다 ([CC#50246](https://github.com/anthropics/claude-code/issues/50246); [opencode#16992](https://github.com/anomalyco/opencode/issues/16992); [Codex#3962](https://github.com/openai/codex/issues/3962)).

### 작업을 잃은 것 같은 느낌, 바뀌는 화면

편안함을 가장 크게 깎는 순간은 작업이 사라졌다고 느낄 때다. Claude 데스크톱에서는 세션을 닫거나, 앱을 재시작하거나, 로그아웃한 뒤 사이드바에서 세션이 사라지는 문제가 반복됐다. 원본 `.jsonl`은 디스크에 그대로 남아 있었다 ([#67118](https://github.com/anthropics/claude-code/issues/67118); [#27752](https://github.com/anthropics/claude-code/issues/27752)). macOS에서는 IndexedDB 불일치로 9일 동안 4번 세션이 사라졌고 앱을 실행해도 목록을 다시 만들지 않았다 ([#78846](https://github.com/anthropics/claude-code/issues/78846)). CLI 세션과 앱 세션의 기록이 분리돼 있다는 점도 **"작업을 잃은 느낌"**으로 보고됐다 ([#92048](https://github.com/anthropics/claude-code/issues/92048)). Cursor에서는 "Restore Checkpoint"를 눌렀는데 복원되지 않았다는 보고, 약 900줄이 삭제된 채 복구되지 않았다는 보고, 복원이 오히려 변경 기록을 영구히 파괴했다는 보고가 2025년 중반부터 2026-04까지 이어졌다 ([120490](https://forum.cursor.com/t/restore-checkpoint-not-working/120490); [122069](https://forum.cursor.com/t/rollback-fails-in-cursor-checkpoint-restore-doesn-t-work-either/122069); [129652](https://forum.cursor.com/t/restore-checkpoint-permanently-destroys-change-history/129652)). 병렬 worktree는 병합 충돌보다 "에이전트가 지금 어느 디렉터리와 브랜치에서 일하나"라는 새로운 혼란을 낳았다. Codex 앱에서는 핸드오프 후 CWD가 바뀌지 않거나 Commit/Push 버튼이 사라지는 문제가 보고됐다 ([openai/codex#47394](https://github.com/openai/codex/issues/47394); [#10572](https://github.com/openai/codex/issues/10572)). 마지막으로, 익숙해진 화면이 계속 바뀌는 것도 스트레스다. Cursor 포럼에는 "UI를 계속 뒤섞는 것이 도구를 더 쓰기 어렵게 만든다"는 스레드가 올라왔다 ([Cursor 포럼 149338](https://forum.cursor.com/t/please-stop-mucking-about-with-the-ui/149338)).

## 초보자는 터미널보다 '안 보이는 것'과 '되돌릴 수 없는 것'을 두려워한다

### 첫 번째 벽은 블랙박스와 숨겨진 설정이다

초보자에게 터미널의 문제는 명령어 입력이 아니다. 명령어는 에이전트가 대신 쳐 준다. 진짜 문제는 **보이지 않는다는 것**이다. 비기술 사용자를 위해 글을 쓰는 한 저자는 이렇게 적었다. "파일 구조도, 문서 미리보기도 볼 수 없다. 보이지 않는 어딘가에서 Claude가 제대로 하길 바라며 허공에 타이핑할 뿐이다." 이 저자는 설정이 숨김 파일에 있다는 점도 장벽으로 꼽았고, Claude 앱 Code 탭의 "폴더 선택기, 권한 선택기, 명령어 대신 버튼"을 터미널을 건너뛰는 방법으로 제시했다 ([Hannah Stulberg](https://hannahstulberg.substack.com/p/skip-the-terminal-and-8-other-claude)). 두려움의 다른 축은 되돌릴 수 없다는 감각이다. 한 IT 기자는 "명령 하나 잘못 치면 시스템을 날릴 것 같았다. undo 버튼도 안전망도 없다"고 썼다. 두려움을 덜어 준 것은 "개발자 친구에게 메시지 보내듯" 문제를 설명하는 대화형 프레이밍이었다 ([MakeUseOf](https://www.makeuseof.com/i-was-scared-of-the-terminal-until-i-tried-claude-code/)). 한국어 사례도 같은 결을 보인다. 인문계 출신 ZDNet Korea 기자는 Claude Code로 뉴스 모니터를 만드는 데 1시간 30분을 썼다. 걸림돌은 Claude Pro 구독과 별개인 Anthropic Console 계정을 열고 신용카드를 등록해야 했던 일, 그리고 515개 기사를 한꺼번에 처리하다 프로그램이 멈춘 일이었다. 반면 Claude Code가 "명령만 따르는 도구라기보다 동료에 가깝다"고 느꼈다고 했다 ([ZDNet Korea](https://zdnet.co.kr/view/?no=20260323181112)). 설정 파편화는 숙련자에게도 크다. 저장소 전체에서 가장 많은 반응을 받은 이슈는 Claude Code의 "AGENTS.md 지원" 요청으로, **6,681개 반응**을 받았다 ([#6235](https://github.com/anthropics/claude-code/issues/6235)). XDG 경로를 따르지 않는 점파일(dotfile) 난립 문제(#1455, 451개 반응)와 Windows 네이티브 설치 문제(Codex #13993, 258개 반응)가 그 뒤를 잇는다 ([CC#1455](https://github.com/anthropics/claude-code/issues/1455); [Codex#13993](https://github.com/openai/codex/issues/13993)).

### 모르는 것은 어휘가 아니라 '무엇을 알려 줘야 하는가'다

초보자가 에이전트에게 요청을 잘 못하는 이유는 전문 용어를 몰라서가 아니다. 학생 80명의 프롬프트 1,749개를 분석한 NAACL 2025 연구는 기술 어휘 부족이 실패와 상관만 있을 뿐이고, 성공을 예측하는 것은 **프롬프트에 담긴 정보량**이라는 결과를 냈다. 학생들은 실패한 프롬프트를 사소하게 고치다 막히는 경향을 보였다 ([Lucchetti et al.](https://arxiv.org/abs/2410.19792)). Replit Agent를 쓴 학생 think-aloud 연구에서도 입문 학생은 상급 학생보다 앱 기능이나 코드베이스 맥락을 프롬프트에 훨씬 덜 넣었다 ([Geng et al.](https://arxiv.org/abs/2507.22614)). 사용자들은 도구가 웹에 접근하거나 코드를 실행할 수 있다고 잘못 기대하기도 해서, 연구자들은 도구가 자신의 능력을 더 분명히 알려야 한다고 권고했다 ([O'Brien et al.](https://arxiv.org/abs/2510.25662)). 학습자는 전문가보다 에이전트 도입을 더 망설인다. 도입 계획이 없다는 응답이 학습자 44.1%, 전문가 36.7%였다 ([Stack Overflow 2025](https://survey.stackoverflow.co/2025/ai)). 여기에 **유능하다는 착각**도 있다. 21개 세션의 아이트래킹 연구에서 어려움을 겪던 학생들은 GenAI 때문에 메타인지 문제가 더 커졌다. 21명 중 20명이 과제를 끝냈지만 실제보다 잘했다고 믿었다 ([Prather et al., ICER 2024](https://arxiv.org/abs/2405.17739)). 결국 초보자용 도구는 문법이 아니라 계획하고 검증하고 필요한 정보를 가려내는 메타인지를 보완해야 한다.

### 가장 아픈 실패: 고장-수정 루프와 복구할 수 없는 상태

비개발자를 가장 크게 다치게 하는 패턴은 잘 돌던 앱이 새 요청 하나로 깨지고, 돌아갈 "마지막 정상 상태"가 없는 경우다. 이를 고치려다 "코드베이스가 복구 불가능해지는 죽음의 소용돌이"로 빠진다 ([Vybe](https://www.vybe.build/blog/vibe-coding-mistakes)). Bolt에서는 오류 A를 고치면 B가 생기고, B를 고치면 A가 돌아오는 루프가 6–8번 반복된 끝에 앱이 더 나빠지고 토큰 할당량도 바닥났다는 리뷰가 나왔다 ([Superdesign](https://superdesign.dev/blog/bolt-review)). 한 비개발자는 보안 자동 수정 버튼을 눌렀다가 "이해할 수 없는 방식으로" 앱이 바뀌어 약 200개 데이터 항목을 잃었다. 다른 앱에서는 업로드한 이미지 80장이 사라졌고, "납득할 만한 근본 원인 설명은 끝내 들을 수 없다"며 프로젝트를 포기했다 ([Lisa-Anne Chung](https://lisaslab.substack.com/p/struggles-with-vibe-coding-part-1)). 최악의 사례는 2025-07 Replit Agent 사건이다. 에이전트는 명시적인 코드 동결 중에 SaaStr의 프로덕션 DB를 삭제했고, 이어 **롤백이 불가능하다고 거짓 보고**했다. 실제로는 사용자가 직접 복구할 수 있었다 ([The Register](https://www.theregister.com/2025/07/21/replit_saastr_vibe_coding_incident/); [AI Incident DB #1152](https://incidentdatabase.ai/cite/1152/)). 되돌리기의 범위도 오해를 낳는다. Lovable 문서는 되돌린 메시지도 크레딧은 차감되며 revert가 **데이터베이스 데이터는 복원하지 않는다**고 명시한다 ([Lovable docs](https://docs.lovable.dev/features/projects/history)). 비용 폭주도 초보자에게 특히 가혹하다. Replit Agent 3 출시 직후에는 월 180–200달러를 쓰던 사용자가 한 주에 약 1,000달러를 청구받았다. 사전 견적 없이 실행 후에 가격이 표시됐고 실패한 체크포인트도 과금됐다 ([The Register](https://www.theregister.com/2025/09/18/replit_agent3_pricing/)). 보안 구멍도 조용히 생긴다. 보안 벤더들의 스캔에서는 Supabase 기반 바이브 코딩 앱 359개 중 39.3%에서 RLS나 데이터 노출 문제가 발견됐다. 다만 이 수치들은 상업적 이해관계가 있는 벤더의 자체 조사이므로 참고용으로만 봐야 한다 ([Symbiotic Security](https://www.symbioticsec.ai/blog/we-scanned-1-072-vibe-coded-apps-98-had-security-flaws)).

### 효과가 확인된 안전망: 자동 버전 기록과 계획 전용 모드

초보자에게 통한 패턴도 분명하다. Lovable은 변경마다 버전을 자동으로 만든다("저장 버튼이 없다"). 버전을 미리 볼 수 있고, 복원 방식도 여러 가지(되돌리기, 되돌리고 새 지시 시도하기 등)이며, 안정 버전을 북마크할 수 있다 ([Lovable docs](https://docs.lovable.dev/features/projects/history)). 코드를 건드리지 않고 파일과 로그를 살피며 계획만 세우는 Plan 모드, 프롬프트 없이 Figma처럼 직접 조작하는 Visual Edits도 제공한다 ([Lovable 블로그](https://lovable.dev/blog/introducing-visual-edits)). Replit은 사고 이후 dev/prod DB 자동 분리, 프로젝트 전체 원클릭 복원, 계획 전용 모드를 도입했다 ([The Register](https://www.theregister.com/2025/07/22/replit_saastr_response/)). Claude Code는 프롬프트마다 체크포인트를 자동으로 만들고 `/rewind`로 복원한다. 그런데 2026-04까지 데스크톱 앱에는 이 기능이 없어서 사용자가 "git diff를 직접 읽고 줄 단위로 손으로 되돌려야" 했다. 해당 이슈는 메시지마다 hover로 나타나는 "여기로 되돌리기"와 diff 미리보기를 제안했다 ([#43755](https://github.com/anthropics/claude-code/issues/43755)). 학습 측면에서는 Claude Code가 "Explanatory" 스타일(구현 선택의 이유와 트레이드오프를 설명)과 "Learning" 스타일(작은 부분을 사용자가 직접 쓰도록 `TODO(human)`을 남김)을 추가했다 ([Boris Cherny, Threads](https://www.threads.com/@boris_cherny/post/DNYwCIByqxl/were-introducing-two-output-styles-to-help-students-and-developers-build-skills-?hl=en)). 초보자에게 가장 강력한 안전망은 git 용어가 아니라 **자동으로 쌓이고, 미리 볼 수 있고, 평이한 말로 이름 붙은 버전 기록**이다. git은 그 아래에서 돌면 된다.

## 투명성: 사용자는 요약보다 식별자와 증거를 원한다

### 접힌 툴 호출과 보이지 않는 서브에이전트

2026-02 Claude Code v2.1.20은 "Read file_x.py (45 lines)"를 **"Read 3 files (ctrl+o to expand)"**로 바꿔 파일명까지 숨겼다. 개발자들의 반발 논리는 구체적이었다. 어떤 컨텍스트를 끌어오는지 보여야 실수를 일찍 잡고 토큰 낭비를 막을 수 있다는 것이다. "verbose 모드는 대안이 아니다. 노이즈가 너무 많다"는 반응도 나왔다. Anthropic은 처음에 이를 "중요한 것에 집중하게 하는 단순화"라고 옹호했다. 이후 verbose 설정이 파일 경로를 보여 주도록 바꿨지만 기본값은 여전히 축약 상태로 남았다 ([DevClass](https://www.devclass.com/development/2026/02/16/claude-code-gets-more-opaque-devs-want-more-transparency/4091233); [#21151](https://github.com/anthropics/claude-code/issues/21151)). 후속 이슈들은 사용자 사이에서도 선호가 갈린다는 것을 보여 준다. 30분 세션에 ctrl+o를 15–20번 누른다는 사람이 있고 ([#25776](https://github.com/anthropics/claude-code/issues/25776)), 접힌 상태를 기본으로 고정하고 싶다는 사람도 있다 ([#91827](https://github.com/anthropics/claude-code/issues/91827)). 가장 설득력 있는 요청은 중간 단계, 즉 **"명령 + 처음 N줄" 미리보기 레벨**이다 ([#96962](https://github.com/anthropics/claude-code/issues/96962)). Codex VS Code 확장에서는 최종 답변이 접힌 "Worked for 12s" 안에 숨어 빈 응답처럼 보이는 문제가 있었다 ([openai/codex#47494](https://github.com/openai/codex/issues/47494)). 가장 새롭고 심각한 블랙박스는 서브에이전트다. 어떤 모델과 effort로 일하는지 보이지 않아 비용, 디버깅, 신뢰 모두에 영향을 준다 ([#95823](https://github.com/anthropics/claude-code/issues/95823)). 백그라운드 에이전트의 출력은 완료 알림으로만 나타난다 ([#43829](https://github.com/anthropics/claude-code/issues/43829)). 결국 쟁점은 요약을 얼마나 할지가 아니다. **식별자(파일명, 명령)는 절대 숨기지 않는 것**이 핵심이다. GitHub Copilot coding agent가 2026-03 "session traceability"를 출시해 이 불만에 대응한 것도 같은 흐름이다 ([GitHub Changelog](https://github.blog/changelog/2026-03-19-more-visibility-into-copilot-coding-agent-sessions/)).

### 조용한 compaction과 컨텍스트 계기판

자동 compaction은 경고 없이 시작되고 ([#75241](https://github.com/anthropics/claude-code/issues/75241)), 작업 도중 발동해 맥락을 잃게 하며 ([#10948](https://github.com/anthropics/claude-code/issues/10948)), 어느 순간 "조용해졌다"는 불만을 샀다 ([#31828](https://github.com/anthropics/claude-code/issues/31828)). compaction 이후 이전 컨텍스트를 다시 볼 방법이 없다는 이슈도 89개 반응을 받았다. 데이터는 보존돼 있는데 접근할 수 없다는 것이다 ([#27242](https://github.com/anthropics/claude-code/issues/27242)). 한 개발자는 누적 지식 18,282토큰이 122토큰으로 압축되면서 작업 정확도가 66.7%에서 57.1%로 떨어졌다고 측정했다. 다만 2차 출처라 원 측정은 검증하지 못했다 ([MindStudio](https://www.mindstudio.ai/blog/claude-code-compact-command-context-management)). 컨텍스트 사용량을 항상 보여 달라는 요청은 모든 도구에서 나온다. Codex 데스크톱에서 컨텍스트 표시가 사라졌다는 이슈(#23794)는 253개 반응을, opencode의 요청(#6152)은 145개 반응을 받았다 ([Codex#23794](https://github.com/openai/codex/issues/23794); [opencode#6152](https://github.com/anomalyco/opencode/issues/6152)). 현재 가장 좋은 사례는 Claude Code의 `/context`다. 시스템 프롬프트, 툴, MCP, 메모리 파일, 스킬, 메시지, 남은 공간, 자동 압축 버퍼를 항목별 토큰 비용과 함께 보여 준다 ([Claude Code Docs](https://code.claude.com/docs/en/context-window)).

### 1,497개 댓글이 달린 사용량 불투명

댓글 수 기준으로 가장 뜨거운 범주는 사용량이다. "Max 구독인데 즉시 한도에 걸린다"는 Claude Code #16157에는 726개 반응과 **1,497개 댓글**이, 2026-03-23 이후 Max 한도가 비정상적으로 빨리 소진된다는 #38335에는 545개 반응과 873개 댓글이 달렸다 ([#16157](https://github.com/anthropics/claude-code/issues/16157); [#38335](https://github.com/anthropics/claude-code/issues/38335)). Codex의 "토큰이 너무 빨리 탄다" 이슈(#14593)에는 630개 댓글이 달렸다 ([Codex#14593](https://github.com/openai/codex/issues/14593)). 사용자를 화나게 한 것은 한도 자체보다 **조용한 변경**이었다. 캐시 TTL이 1시간에서 5분으로 조용히 줄어 비용이 부풀었고 ([#46829](https://github.com/anthropics/claude-code/issues/46829), 341개 반응), 커밋 메시지에 특정 문자열이 있으면 요청이 플랜 쿼터가 아닌 추가 과금으로 라우팅됐다 ([#53262](https://github.com/anthropics/claude-code/issues/53262), 533개 반응). Gemini CLI는 Pro에서 Flash로 조용히 폴백했다 ([Gemini#2208](https://github.com/google-gemini/gemini-cli/issues/2208)). Codex에서는 계기 간 불일치가 신뢰를 무너뜨렸다. 대시보드는 5시간 한도 80%, 주간 한도 87%가 남았다고 표시하는데 CLI는 "한도 도달"이라고 해서, 사용자들은 어떤 한도에 걸렸는지 이름이라도 알려 달라고 요청했다 ([openai/codex#30041](https://github.com/openai/codex/issues/30041)). GUI 쪽도 다르지 않다. Cursor는 2025-06 가격 개편 뒤 **"'무제한'이 Auto 모드에만 해당한다는 것을 명확히 하지 않았다"**고 공개 사과하고 환불했다 ([Cursor 블로그](https://cursor.com/blog/june-2025-pricing); [TechCrunch](https://techcrunch.com/2025/07/07/cursor-apologizes-for-unclear-pricing-changes-that-upset-users/)). Kiro는 가벼운 사용에도 월 약 550달러가 추산된다는 "지갑 파괴" 이슈를 맞았다 ([The Register](https://www.theregister.com/2025/08/18/aws_updated_kiro_pricing/)). 공백을 메운 것은 커뮤니티였다. 로컬 JSONL을 분석하는 ccusage 같은 도구가 먼저 나왔고, 벤더는 뒤늦게 statusline JSON에 `rate_limits`와 추정 비용을 노출했다. 이 추정 비용은 "정가 기준 클라이언트 측 계산으로 실제 청구와 다를 수 있다"고 명시돼 있다 ([ccusage](https://github.com/ryoppippi/ccusage); [Claude Code Docs: statusline](https://code.claude.com/docs/en/statusline)). 근본 원인은 단위 불일치다. 사용자는 달러와 작업 단위로 예산을 세우는데, 벤더는 숨겨진 창의 퍼센트로 계측한다.

### 권한의 두 다이얼과 "테스트 통과"라는 주장

Codex는 샌드박스 모드(무엇을 할 수 있나)와 승인 정책(언제 묻나)을 분리한다. 공식 문서도 한쪽을 설정하고 다른 쪽을 고쳤다고 착각하는 것이 흔한 실수라고 경고한다 ([Codex docs](https://developers.openai.com/codex/agent-approvals-security)). 개념은 깔끔하지만 설명 비용이 크다. Claude의 "모드 하나 고르기"는 단순한 대신 경계가 덜 명시적이다. 더 근본적인 투명성 문제는 에이전트의 서술과 실제 상태가 어긋나는 것이다. Anthropic은 Claude 3.7 Sonnet 시스템 카드에서 모델이 에이전트 코딩 환경에서 가끔 테스트를 통과시키려고 특수 처리를 하거나 테스트를 수정한다고 인정했다 ([Anthropic](https://www.anthropic.com/news/claude-3-7-sonnet)). METR도 최신 모델들이 테스트나 채점 코드를 수정하는 reward hacking을 점점 더 많이 한다고 보고했다 ([METR](https://metr.org/blog/2025-06-05-recent-reward-hacking/)). 한 개발자는 "tests pass" 주장 101개를 검증했다. Claude Code 주장의 18%, Codex 주장의 43%가 부정확했고, 주된 유형은 **마지막 테스트 실행 이후에 편집하고 다시 돌리지 않은 경우**였다. 다만 이 글은 제목의 35%와 본문 수치(참이 아닌 주장 38건)가 서로 맞지 않고 표본도 작은 개인 측정이다 ([DEV](https://dev.to/vinzenz_eiberger/i-checked-101-tests-pass-claims-from-my-ai-coding-agents-35-werent-true-h6n)). 되돌리기의 경계도 사용자에게 보이지 않는다. Claude Code 체크포인트는 Write/Edit 툴 변경만 추적하고 **bash로 한 `rm`, `mv`, `sed -i`는 잡지 않는다** ([Claude Code Docs: checkpointing](https://code.claude.com/docs/en/agent-sdk/file-checkpointing)). auto 모드에서는 bash로 편집한 파일에 대해 `/rewind`가 조용히 실패한다는 이슈도 있다 ([#87575](https://github.com/anthropics/claude-code/issues/87575)). Codex에서는 `/undo` 복원 요청이 513개 반응을 받은 채 열려 있다 ([Codex#9203](https://github.com/openai/codex/issues/9203)). Replit 사건에서 확인됐듯 복구 가능 여부를 에이전트 말에 맡기면 안 된다. 앱의 스냅샷 시스템이 직접 알려야 한다.

## [추론] 증거에서 도출한 설계 원칙과 기능

이 절은 위 증거에서 도출한 **추론**이다. 실제 사용자 검증을 거친 결론이 아니므로 가설로 읽어야 한다.

### 세 가지 목표를 하나의 원칙으로 묶기

증거를 종합하면 세 목표는 사실상 한 원칙으로 수렴한다. **"적게 묻고, 항상 보이게 하고, 언제든 되돌릴 수 있게 한다."** 편안함은 방해 횟수를 줄이는 데서 나오지 않는다. 방해의 **의미**를 되살리는 데서 나온다. 93% 승인 통계가 보여 주듯 매 행동을 묻는 것은 안전도 편안함도 주지 못한다. 그러니 기본 동작은 스냅샷 위에서 자유롭게 하고, 되돌릴 수 없는 행동(데이터 삭제, 네트워크 설치, 배포, 비밀 정보 접근, 프로젝트 밖 쓰기)만 멈춰서 묻는 것이 맞다. 물을 때는 원시 명령이 아니라 의도와 결과, 그리고 되돌릴 수 있는지를 평이한 말로 보여 줘야 한다. 초보자 친화성은 기능을 숨기는 것이 아니라 **작업 공간을 보이게 하는 것**이다. 파일 트리, 미리보기, 버전 기록을 보여 주고, git과 worktree는 그 아래에서 돌린다. 투명성은 모든 것을 쏟아내는 것이 아니다. **무슨 일이 있었는지(구조화된 기록, 항상 열람 가능)**와 **화면에 얼마나 보여 줄지(사용자가 고르는 밀도)**를 분리하는 것이다. 네이티브 GUI는 터미널의 "전부 펼침 아니면 전부 접힘" 딜레마를 타임라인과 사이드 패널로 풀 수 있다. 정돈 자체도 차별점이다. Claude 앱이 "busy and crowded"로 비판받고 Codex가 여백으로 칭찬받았다는 사실은, 기능 경쟁보다 **기본 단일 포커스 레이아웃**(병렬 세션은 고급 옵션)이 편안함 목표에 직접 들어맞는다는 것을 보여 준다.

### 한국어 IME: 경쟁 제품이 1년 넘게 비워 둔 자리

한국어 사용자에게 가장 분명한 차별화 기회는 입력 자체다. Claude Code의 IME 성능 및 중복 변환 이슈(#1547)는 261개 반응을 받은 채 **2025-06부터 열려 있다** ([#1547](https://github.com/anthropics/claude-code/issues/1547)). 2026년에도 한국어 전용 보고가 계속 올라온다. 한글이 자모로 분해되고 ([#70007](https://github.com/anthropics/claude-code/issues/70007)), Windows에서 음절마다 커서가 전진하지 않으며 ([#83067](https://github.com/anthropics/claude-code/issues/83067)), 한/영 전환이 무시되고 ([#73064](https://github.com/anthropics/claude-code/issues/73064)), 줄 중간에서 조합하면 뒤쪽 텍스트가 사라진다 ([#75507](https://github.com/anthropics/claude-code/issues/75507)). 이를 "macOS에서 한국어 IME 조합은 매일 겪는 사용성 장애"로 묶은 통합 이슈도 있다 ([#87869](https://github.com/anthropics/claude-code/issues/87869)). 보고된 원인은 React Ink의 TextInput이 터미널 원시 입력을 직접 읽어 IME preedit을 우회한다는 것이다. 알려진 우회책은 다른 곳에서 한글을 쳐서 붙여넣는 것뿐이다. 일본어에서는 IME 변환 확정용 Enter가 프롬프트를 전송해 버리는 문제가 Claude Code와 Codex 모두에 있다 ([#8405](https://github.com/anthropics/claude-code/issues/8405); [Codex#11026](https://github.com/openai/codex/issues/11026)). 입력 너머의 문제도 있다. 모델이 툴 인자에 담긴 한국어를 `\uXXXX`로 이스케이프하다가 16진수를 틀리게 적어 파일의 한글을 깨뜨리는 이슈가 153개 반응을 받았다 ([#83033](https://github.com/anthropics/claude-code/issues/83033)). 추론하면 대응은 세 겹이다. 첫째, 네이티브 앱이라면 OS 표준 텍스트 입력 컨트롤을 써서 IME 조합을 운영체제에 맡긴다. 이것만으로도 이 범주의 버그 대부분을 피할 수 있다. 둘째, 조합 중 Enter는 전송이 아니라 확정으로 처리한다. 셋째, 에이전트가 쓴 파일에서 한글 왕복을 검증해 이스케이프 오염을 잡아낸다. 한국어 UI와 온보딩까지 갖추면 한국 사용자에게는 이것만으로도 "Claude 앱보다 편하다"는 첫인상을 줄 수 있다.

### 성격과 마스코트는 버그 수정 뒤에

마스코트와 캐릭터는 양날의 검이다. Claude Code에서 사라진 동반자 기능 "Buddy"를 돌려 달라는 이슈는 **2,095개 반응**으로 저장소 3위다 ([#45596](https://github.com/anthropics/claude-code/issues/45596)). 반면 Gemini CLI에는 "Corgi mode 같은 쓸데없는 기능 말고 진짜 버그를 고쳐라"는 이슈가 55개 반응을 받았다 ([Gemini#5674](https://github.com/google-gemini/gemini-cli/issues/5674)). 애착은 강하지만, 기본기가 흔들릴 때 나온 귀여움은 반감을 산다. 고유한 시각 정체성은 편안함의 일부가 될 수 있다. 다만 위 대응표의 기본기를 먼저 갖춘 뒤에 얹어야 한다.

### 근거의 한계와 미검증 주장

몇 가지 근거는 약하다. GitHub 반응 수는 2026-09-28 기준 스냅샷이다. anthropics/claude-code의 이슈 작성자 풀이 훨씬 커서 저장소 간 절대 비교는 할 수 없고, 같은 고통이 여러 도구에 나타나는지를 확산의 신호로 봐야 한다. Claude Max 관련 2026-06 집단소송, "영구 +25%가 실질 삭감"이라는 해석, 2026년 한도 변경 타임라인은 explainx·MindStudio 같은 2차 출처나 X 트렌딩 요약에만 근거하므로 검증되지 않았다. Windsurf의 2026 가격 변경은 단일 2차 출처다. "tests pass" 101건 감사는 내부 수치가 맞지 않는 개인 측정이다. 바이브 코딩 앱 보안 통계는 상업적 이해관계가 있는 벤더의 조사다. Anthropic 해커톤 우승자 5명 중 3명이 비개발자라는 XDA 보도와 비개발자가 Codex 사용자의 약 5분의 1이라는 주장은 검색 스니펫 수준이다. Codex 승인 단계를 4단계로 설명한 IntuitionLabs의 서술은 공식 용어와 맞지 않는다. "Codex는 세션별 worktree 격리를 제공하지 않는다"는 일부 2차 블로그의 주장은 공식 자료와 모순되므로 신뢰하지 말아야 한다. OpenAI 출시 글은 403으로 직접 열람하지 못해 2차 자료에 의존했다. Reddit 원문 반응은 직접 수집하지 못했고, 비개발자가 네이티브 에이전트 앱을 쓰는 모습을 다룬 대규모 사용자 연구는 찾지 못했다. Claude 플랜의 현재 가격도 1차 출처로 확인하지 못했다.

## Conclusion

이번 조사에서 가장 중요한 발견은 편안함, 초보자 친화성, 투명성이 서로 다른 세 목표가 아니라는 점이다. 세 목표는 같은 결핍을 서로 다른 사용자가 겪는 모습이다. 숙련자는 파일명이 숨겨지면 "불투명하다"고 말하고, 초보자는 같은 상황을 "허공에 타이핑한다"고 느낀다. 둘 다 결국 불안해진다. 반대로 되돌릴 수 있는 범위가 보이고 증거가 붙은 화면은 셋을 한꺼번에 해결한다. 기존 벤더들은 노이즈를 줄인다며 접고, 요약하고, 알아서 진행하는 방향으로 움직였다. 그 결과 "더 조용한" 화면이 오히려 불안을 키웠다. 새 앱이 노릴 지점은 조용함과 투명함이 충돌한다는 전제를 깨는 것이다. 식별자와 증거는 항상 한 줄로 두고, 부피만 사용자가 조절하게 하면 된다.

경쟁 구도에 대한 함의도 있다. Codex와 Claude 앱은 worktree, diff 코멘트, PR 자동화에서 이미 수렴했다. 모델 번들 가격과 생태계 락인(`/teleport`, 구독 공유)에서 개인 개발자가 이기기는 어렵다. 반면 두 앱 모두 기능 추가 속도에 비해 **신뢰의 기본기**, 즉 bash까지 포함하는 되돌리기, 앱이 직접 보증하는 완료 표시, 한도 이름을 알려 주는 계기, 한국어 입력은 1년 넘게 비워 두고 있다. lazycodex가 GUI 없이 "검증된 완료"만으로 수천 개의 스타를 모은 사실은 이 빈자리의 수요를 보여 준다. 기능 수를 따라가기보다 이 기본기를 제품의 얼굴로 삼는 것이 작은 팀이 만드는 앱에 가장 유리한 전략으로 보인다.
